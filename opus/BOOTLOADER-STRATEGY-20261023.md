# Стратегия стабильной загрузки нового ядра — 2026-10-23

Это анализ и план реализации. Планшет остаётся в штатном Android.

## Подтверждённые результаты

ABL-entry-probe успешно рисовал шахматную заливку: ABL исполняет наш ARM64
payload, framebuffer доступен. Это наиболее короткая доказанная граница входа.
U-Boot v3 не достиг наблюдаемой инициализации; v4 — инструментированный
граничный тест с намеренным wfe, а не готовый USB-загрузчик.
r70 доходил до initramfs по фото, но без PINCTRL_MSM; работу SD это не доказывает.
r120 завершил sync/WLAN unbind/watchdog disable и вызвал kexec -e, затем
получен новый boot_id 4.19. Где произошёл reset, неизвестно.
PS_HOLD не устанавливает инициатора. panic=0 второго ядра не исключает
panic первого ядра с его panic=-1 или аппаратный/firmware reset.

## Выбор архитектуры

Основной кандидат: Lenovo ABL → минимальный stage0/U-Boot → Linux 6.12
с initramfs → USB-консоль → microSD → Arch multi-user → графика.
Причина выбора: исключить завершение работающего 4.19 и унаследованные
состояния его устройств из основного пути. Это уменьшает число неизвестных,
но само по себе не гарантирует рабочие RPMh, USB или SD.
ABL/заводские bootloader-разделы не заменять. Stage0 испытывать через
существующий временный recovery workflow с восстановлением stock-пары.
После доведения USB stage0 новые payload передавать в RAM через его fastboot.
U-Boot FASTBOOT_FLASH и доступ к накопителям для первого этапа отключены.

## Порядок разработки и критерии

1. Повторно проверить исходники v4 и точную границу остановки: reset entry,
   получение DT, RAM banks/reserved ranges, relocation, board init, USB.
   Убрать намеренный wfe только в новой ревизии; оставить короткие уникальные
   экранные маркеры. Никакого вывода об успехе только по упаковке.
2. Довести USB fastboot с серийным номером TB371FC-UBOOT. Принимать загрузчик
   после повторяемых холодных запусков и нескольких передач payload в RAM.
3. Linux 6.12 сначала минимальный initramfs без microSD и графического modeset.
   Требовать uname 6.12, растущий uptime, доступную командную оболочку/USB,
   отсутствие reset при наблюдении. Старый framebuffer не доказательство.
4. Затем SD: встроенные pinctrl/SM8250/GCC/SDHCI и необходимые поставщики;
   проверить actual_clock, ответ карты и block device именно под 6.12.
   Не переносить warm-kexec обходы питания/CXO автоматически в cold-boot DT.
5. Arch multi-user с журналом на SD; только затем DRM/Mesa/KDE.

## Контрольный путь kexec

Сравнить r70 и r118 с одинаковыми first-stage, DTB, initramfs и cmdline,
меняя один компонент за тест. В первом ядре проверить kernel.panic перед
execute: его panic=-1 мог скрывать ошибку shutdown. Поставить panic=0 в
RAM для диагностического запуска и наблюдать экран. Это гипотеза, не фикс.
Если reset происходит и с r70, локализовать first-stage shutdown/entry;
если только r118 — проверить ранние изменения и размещение rebuilt Image.
RAM-маркеры теряются при reset; pstore использовать лишь после проверки
безопасного reserved-memory региона и поддержки обоих ядер.

## Риски, которые надо закрыть до обычной эксплуатации

Статический relocation shim использует 0x92000000 и фиксированный шаг cache
line 64: это не доказанная универсально безопасная схема. Проверять окна
Image/initrd/DTB/stage0/firmware/reserved-memory, выравнивание и boot protocol.
Не называть новый образ стабильным до повторяемого аппаратного запуска.
Подготовленные 7.x payload не доказывают запуск 6.12 и не меняют целевую версию.
