# Linux 6.12 r120 — 2026-10-01

Статус: recovery собран и прошёл аудит. Аппаратная загрузка не подтверждена.
После переподключения обнаружен <serial>, recovery_b и test vbmeta_b
прошиты штатным проверяющим скриптом (оба OKAY). Первый этап поднял COM9.

## Аппаратный тест r120

SSH подтвердил 4.19, boot_id f9ddd60f-fa77-4cb1-b4d4-2bd11a71f199.
Payload проверен и загружен. Все R120 HANDOFF отметки получены вплоть до
`calling kexec -e`: sync, WLAN unbind, watchdog write завершились.
Лог: `hardware-handoff-20261001.log` в каталоге сборки.
SSH затем завершился Connection reset. Windows ещё перечисляет COM9,
но новый мост получает SerialTimeoutException при записи CRLF.
Это не подтверждает возврат к 4.19 и не доказывает запуск 6.12.
Нужно состояние экрана: USB второго ядра отключён в DT.

Повторная SSH-проверка после фото image-01-10-26-10-05 подтвердила RESET:
uname снова 4.19.157-perf-v56.6+, boot_id теперь
f8a62069-beb7-4b09-a606-e5376bef30a3 (до execute был
f9ddd60f-fa77-4cb1-b4d4-2bd11a71f199), uptime 312.30, kexec_loaded=0.
RAM handoff log отсутствует. PMIC SID0: Hard Reset/cold boot, power-off
PS_HOLD/MSM Controlled Shutdown. Это подтверждает перезагрузку, но не
устанавливает её инициатора. panic=0 задан второму ядру; первый этап
сохраняет panic=-1. Нельзя исключить сбой первого ядра в shutdown/kexec.
Лог: post-handoff-status.log рядом с образом. Следующий шаг — локализовать
reset между вызовом kexec, shutdown первого ядра и входом во второе,
с контролем на ранее доходившем до initramfs r70 и тем же транспортом.

## Исправление прошлых выводов

microSD в выводе uname 4.19 доказывает работу только первого этапа.
Объявлять SD исправленной в 6.12 было ошибкой. Обрыв SSH не устанавливает
место остановки. Мост обслуживает одну TCP-сессию; connection refused при
повторном подключении к занятому мосту не доказывает сбой планшета.

r99–r117 доходили до initramfs по фотографиям, но exact r70 отключает
PINCTRL_MSM. Исправления pinctrl и CXO /2 уже есть в r118, который затем
перезагружался. Причина reset остаётся неизвестной; возвращаться к r102
как к новой разработке ошибочно. См. R118-PINCTRL-CLOCK-REVIEW.md.

## Причина сбоя сборки r102

Полная bash xtrace выявила выход на проверке
`grep -Fq TB371FC_SERIAL_SSH_SESSION_TIMEOUT:-300 .../tb371fc-development-init-runtime`.
Текущий runtime проекта не содержит этот маркер и STREAM_CLOSED.
Это не неисправность WSL или прокси. r120 использует runtime из проверенного
по SHA256 recovery r101, сохраняя текущие пользовательские исходники.

## Следующий аппаратный тест

После обнаружения <serial> в fastboot запустить штатный LaunchFastboot с
RecoveryImage r120 и TwoPartitionWriteApproved. На COM9 открыть один мост
и одну SSH-сессию; записать вывод на ПК и выполнить:

`/run/tb371fc-rescue/load-linux-6.12-r38 && /run/tb371fc-rescue/execute-linux-6.12-r38`

Критерии успеха: подтверждённое ядро 6.12, ненулевая actual_clock MMC,
ответ SD и mmcblk0p1 под вторым ядром, затем Arch multi-user.
Ни успешная упаковка, ни исчезновение COM9 этого не доказывают.
