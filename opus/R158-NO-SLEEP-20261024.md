# R158: the "random" full hangs were KDE idle suspend

2026-10-24. Installed: recovery_b = R158 (d3464681…), SD `tb371fc-linux/autoboot-6.12-r158`.

## Diagnosis

R153 and R157 froze with a dark screen, no input, no ping. Captured on R157 with a
continuous `dmesg -w` and a 30 s liveness probe: the freeze came ~15 min after KDE
started, fully idle (load 0.00, PMIC temps 32–37 °C), with no kernel message at all.
Kernel offers `mem_sleep [s2idle]`; KDE PowerDevil's default idle suspend (~15 min)
puts the system into s2idle, which has no working wake path on this port.
With `systemctl mask --runtime sleep/suspend/hibernate/hybrid-sleep/suspend-then-hibernate`
the same idle system survived 27 min (`diagnostics/r158-nosleep-watch-20261024.log`).
So the hangs were not Wi-Fi and not the 8 CPUs; R153's Wi-Fi was likely innocent.

Unrelated observation kept for later: every boot prints a WARNING at
include/linux/sched.h:2252 (`set_blocked_on_waking_nested`, ACK proxy-exec `blocked_on`
tracking) from drm_modeset_lock in KWin's atomic ioctl. The system keeps running.

## R158

R157 + `scripts/r158-config/r158-install.sh` run from the boot hook before the touch/KDE
units: masks all sleep targets for the boot (RAM). Payload `D:/TB371FC-builds/r158-nosleep`
(initramfs 05111101…), recovery `…/linux-6.12.30-tb371fc-r158-autoboot-20261024`
(`scripts/package-r158-autoboot-recovery.py`, AUDIT_RESULT=PASS), SD via
`scripts/r158-sd-install.sh`. Boot 3d974ea9…: sleep targets masked-runtime, touch, keyboard,
KDE active. Rollback R157 (f7cf5491…).
