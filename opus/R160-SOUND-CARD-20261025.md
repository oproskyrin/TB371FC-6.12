# R160: звуковая карта есть; запуск PRI_TDM вешает систему (звук, этап 2), 2026-10-25

## Итог R160b (обновление): путь MM1 → PRIMARY_TDM_RX_0 работает

Причина «зависаний» найдена по полному oops (diagnostics/r160-steps-20261025.log):
`qcom_snd_sdw_startup+0x7c` ← `sm8250_snd_startup` при открытии PCM. В 6.12
`snd_soc_dai_set_stream()` разыменовывает `codec_dai->driver->ops` без проверки на NULL,
а у кодека-заглушки spdif-dit ops нет. Вся система вставала из-за `CONFIG_PANIC_ON_OOPS=y`
+ `PANIC_TIMEOUT=-1`: перезагрузка из паники на этой плате не работает. С
`panic_on_oops=0` oops убивает только процесс. Гипотеза про голос LPASS не подтвердилась
(модуль tb371fc-lpass-vote оставлен, вреда нет, в mainline эти голоса держит LPI pinctrl).

Исправления (R160b):
- машинный драйвер для PRIMARY_TDM_RX_0 не вызывает qcom_snd_sdw_startup (как в upstream
  2025 «ASoC: qcom: sdw: fix memory leak», где sdw-функции вызываются только для sdw-DAI);
- BE S16_LE (16 бит в 32-битных слотах): q6routing 6.12 знает только S16/S24 для ADM;
- DT R160b (b9aafdb7…, `scripts/prepare-r160b-sound-dt.sh`): q6asm `dai@0..2`, штатный q6asm-dai.

Проверка (boot a17c02b9…, `scripts/r160b-bringup.sh`, `scripts/r160b-tdm-steps.sh`,
`scripts/r160b-aplay-check.sh`): pcm-steps open/hw_params(4 ch, 48 кГц, 16 бит)/prepare/
write 3840 кадров/drop/close — все rc=0; aplay 3 с длится 3 с (DSP потребляет поток),
ошибок q6afe/q6asm/q6adm нет, ADSP/CDSP/SLPI running. Усилители выключены, TDM-выводы не
переключены, звука нет. Следующий этап: pinctrl TDM-выводов, ID динамиков (GPIO 1171 → YC/QS),
драйвер TFA9894 при нулевой громкости.

Итог: на R159-ядре с DT R160 появилась ALSA-карта `card0 Lenovo-TB371FC` (PCM MultiMedia1,
1026 элементов микшера). Проигрывание без маршрута проходит. Как только MultiMedia1
подключён к PRIMARY_TDM_RX_0 и запущено проигрывание нулей, система полностью зависла
(нет SSH и ping, экран застыл). Усилители TFA9894 выключены, TDM-выводы не переключались,
значит звука не было и быть не могло. Логов зависания нет — dmesg не успел выйти.

## Что сделано

- Машинный драйвер `snd-soc-tb371fc` = 6.12 sm8250.c + PRI_TDM_RX_0: 4 слота × 32 бита,
  смещения 0/4/8/12, бит-клок 6,144 МГц (Q6AFE_LPASS_CLK_ID_PRI_TDM_IBIT), BE S32_LE/4ch/48 кГц.
  `scripts/r160-sound/make-tb371fc-sndcard.py`, `scripts/build-r160-sound-modules.sh`
  (snd-soc-tb371fc.ko 6e819dd4…, snd-soc-spdif-tx.ko cdca4673…).
- DT R160 (65b38f14…, `scripts/prepare-r160-sound-dt.sh`): q6afe dai@24 с параметрами Lenovo
  (sync-mode 1, sync-src 1, data-out 0, invert-sync 1, data-delay 1, data-align 0), карта
  `lenovo,tb371fc-sndcard`, кодек-заглушка `linux,spdif-dit`.
- Ошибка DT: у q6asm-dais нет дочерних `dai@N`, q6asm-dai отказывается (EINVAL). Для живой
  проверки собран q6asm-dai с подстановкой MultiMedia1 (`scripts/build-r160-q6asm-dai-fallback.sh`,
  c58a98e9…). В следующем DT добавить `dai@0..` под service@7/dais.
- Имя элемента микшера в 6.12: `PRIMARY_TDM_RX_0 Audio Mixer MultiMedia1` (не PRI_TDM_RX_0).

Логи: diagnostics/r160t-launch-20261025.log, r160-sound-20261025.log, r160-sound2-20261025.log,
r160-silence-20261025.log (обрывается после `values=on`).

## Гипотезы зависания (не проверены)

1. Запуск AFE-порта TDM требует питания/клоков LPASS (аудио-ядро, LPASS GDSC, MCLK), которые
   в 4.19 включал vendor-драйвер, а здесь не включены; доступ DSP или ядра к выключенному блоку
   вешает шину.
2. Голосование за бит-клок PRI_TDM через q6afe-clocks на этой прошивке ADSP ведёт себя иначе.
3. Что-то в последовательности routing/ADM (q6adm) на этой прошивке.

## R161: усилители TFA9894 подключены (звук, этап 3), 2026-10-25

  direction=in, value=1 → по логике стокового audio_tfa98xx.ko второй контейнер **tfa98xx_QS.cnt**
  (a3f64160…). Лог diagnostics/r161-419-recon-20261025.log. В DT 4.19 узлов TFA нет.
- Драйвер: community TFA98xx (patch 0003) внешним модулем, `scripts/build-r161-tfa98xx.sh`
  (bfcd66c7…), правка API 7.1→6.12 и **защита MTP** `scripts/r160-sound/tfa98xx-mtp-guard.py`:

- DT R161 (3ddc9d58…, `scripts/prepare-r161-tfa-dt.sh`): существующие узлы amplifier@34..37 на
  **i2c@884000** (QUP2 SE15, выводы 44/45; первая попытка на 990000 была ошибкой — там SPI-протокол),

  PRI TDM pinmux на узле sound, кодеки speaker-ссылки = 4 усилителя.

  задаётся амплитудой сигнала. Проигрывания не было.
