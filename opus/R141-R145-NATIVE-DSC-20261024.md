# R141–R145: native DPU/DSI/DSC on 6.12 — first native picture

2026-10-24. Every run: RAM kexec from first-stage 4.19, no flash, SD read-only.
Kernel uname stays `6.12.30-tb371fc-r137-native+` (LOCALVERSION kept so the
R139 initramfs modules load); identify builds by Image SHA256.

## R141 — DPU-only (GPU/GMU disabled) + R140 MMCX fix

DT = R139 + framebuffer power-domains=MMCX/required-opps=NOM + gpu@3d00000 and
gmu@3d6a000 `status=disabled` (msm_drv.c add_gpu_components skips them).
Package `D:/TB371FC-builds/r141-dpu-only`, DTB 2d11e9fe…, script
`scripts/prepare-r141-dpu-only.sh`, runner `scripts/test-r121-r141-dpu-only.sh`.

- Boot bccfdba3…: console visible, mmcx 256. Stages power/dispcc/icc/backlight
  all OK; MDSS/DPU/both DSI/PHY bound. Screen went black at the MDSS stage
  (msm-mdss resets MDSS on probe and kills the splash), as expected.
- Step 6 (full panel probe): `Initialized msm`, "no GPU device was found",
  then the same hang as R139. **So Adreno/SQE firmware is not the cause.**
- R141b (boot 2d710c27…): with `/sys/module/msm/parameters/fbdev=N` step 6
  completes and the system stays up: the hang is the **first modeset**.
  Connector DSI-1 has 4 modes (120 preferred, 144, 60, 30).

## R142 — ramoops (did not survive) and printk_delay (worked)

ramoops@9e380000 (inside 4.19's reserved dfps region) registered fine, but the
log did not survive the long-press reset. 4.19 has no pstore and no /dev/mem.
`echo 40 > /proc/sys/kernel/printk_delay` + `dmesg -w` over USB captured the
whole failure: `dpu_encoder_virt_atomic_mode_set: no ctl block assigned at
idx: 1`, then **NULL pointer dereference in dpu_crtc_atomic_begin**
(panic=0, 1 CPU => silent hang). Log `diagnostics/r142-dmesg-follow-20261024.log`.

## R143 — patch 0010: keep bonded intf count with DSC

6.12 `dpu_encoder_get_topology()` forces `num_intf = 1` for DSC, so only one
CTL is reserved for two physical encoders. 7.1 keeps the real count.
Patch `mainline-port/backports/linux-6.12/0010-dpu-dsc-keep-bonded-intf-count.patch`,
build `scripts/build-r143-dsc-intf.sh`, Image 3ac85041….
Result (boot 1217a801…): **no crash**; panel init commands sent over both DSI;
commit kickoff done; but continuous DSI FIFO errors (`dsi_err_worker status=4`)
and SMMU context faults. Screen black.

## R144 — patch 0011: round DSC INTF width up

DPU INTF width = 1472*8/24 = 490 (truncated) while DSI ACTIVE_H and downstream
`pclk_per_line` use DIV_ROUND_UP(1472 bytes, 3) = 491.
Patch `0011-dpu-dsc-intf-width-round-up.patch`, build `scripts/build-r144-dsc-width.sh`,
Image 9df14a30….
Result (boot 37b4a3f0…): **DSI errors 0**. Photo
`diagnostics/r144-modetest-photo2-20261024.jpg`: **left half of the panel shows
the correct modetest SMPTE pattern via native DSI0+DSC0**; right half (DSI1)
garbage. SMMU faults remain: MDP (SID 0x820/0xc20) reads up to ~31 lines past
the end of the 21.6 MB buffer (iova 0x3000+0x14aa000), plane uses parallel
multirect sspp_0 rect_0/rect_1 (1472 px each).
Tests used `modetest -M msm -s 33@89:2944x1840-60` with stdin held by `sleep`.

## R145 — per-CTL DSC ownership: WORSE, rejected

With 2 CTLs, 6.12 sets CTL_DSC_ACTIVE of both CTLs to DSC_0|DSC_1 and flushes
both DSCs only through the master CTL. R145 made each CTL own/flush only its
own DSC (`scripts/apply-r145-dsc-ctl.py`; the .patch file did not apply, the
applied diff is `D:/TB371FC-builds/r145-dsc-ctl/dpu1-full.diff`), Image f3dded21….
Boot ee094456…: console visible at boot (photo r145-boot-console-photo), DSI
errors 0, SMMU faults unchanged. Photo `diagnostics/r145-modetest-photo-20261024.jpg`:
left half now noisy and stretched, right half still garbage. **R144 remains the
best native build.** Do not reuse 0012 as is.

Next ideas (one at a time, on top of R144):
1. Port 7.1's single-CTL model for active-CTL hardware (rm reserves 1 CTL,
   both phys encoders share it, CTL_INTF_MASTER) — closest to downstream SDE.
2. Check DSC PPS pic_width per DSI (1472 vs 2944) and `enc_ip_w`
   (736 vs downstream 1472) for split-panel mode.
3. Find the SMMU over-fetch (rect_1 / tail of buffer).

## R146 — 7.1 single-CTL model on top of R144

`scripts/apply-r146-single-ctl.py` (rm reserves 1 CTL on DPU>=5, both phys
encoders share it, CTL_INTF_MASTER from 7.1), build `scripts/build-r146-single-ctl.sh`,
Image 00b78e9d…, boot 6c08cf3f…. modetest running: **SMMU faults 0, DSI errors 0**.
Photo `diagnostics/r146-modetest-photo-20261024.jpg`: the whole panel is lit,
both halves receive data, but both show the same garbage (vertical stripes).
So flushing/ownership is now consistent; the remaining problem is the DSC
encoder configuration (or PPS/pic_width/enc_ip_w) for the shared-CTL pipe.
Best next step: dump DPU CTL/DSC/PP/INTF registers on working 4.19 V56
(earlier /root/mdss-dsc-dump-build work) and compare with R146.
